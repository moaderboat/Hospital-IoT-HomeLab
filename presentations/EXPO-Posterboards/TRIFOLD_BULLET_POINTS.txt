OPTION 1 - Condensed paragraph (current):
Healthcare Internet of Things devices face unprecedented security challenges that directly impact patient safety and hospital operations. This project demonstrates defense-in-depth security architecture through a fully functional hospital patient monitoring network and live attack scenario comparing vulnerable and hardened system configurations with identical hardware.

Our infrastructure consists of nine Ubuntu Server virtual machines providing hospital IT services (database management, MQTT messaging, HL7 FHIR transformation, SIEM, identity management, and secrets management) and seven Raspberry Pi devices. Five Pi units generate realistic cardiac telemetry representing distinct patient profiles, while two units serve as attack demonstration controllers. The system processes 100 sensor readings per second through an HL7 FHIR-compliant pipeline, maintaining over 53 million database records with zero data loss.

The attack demonstration compares identical pressure sensor systems with dramatically different outcomes. The vulnerable system implements a Flask HTTP API with no authentication or input validation. When an attacker sends spoofed "0.0 PSI" readings at 10 Hz, the system blindly accepts the data, causing catastrophic vessel failure within 20 seconds with no security logging. The secure system validates all network data against local I2C sensor measurements, detecting the mismatch and rejecting all attacks while maintaining safe operation. Every attack is logged to Wazuh SIEM with complete forensic details, and all traffic is captured by Suricata IDS and visualized in real-time Grafana dashboards.

=====================
THE PROBLEM (LEFT PANEL)
=====================

Healthcare IoT Security Crisis:
• 82% of healthcare organizations hit by ransomware in past year
• Average breach cost: $10.9 million (highest of any industry)
• 400+ U.S. hospitals forced to divert ambulances during ransomware incidents
• 465,000 pacemakers recalled due to cybersecurity vulnerabilities

Patient Safety Impact:
• Real-time monitoring systems are life-critical infrastructure
• Device failure or data manipulation can directly threaten patient safety
• Compromised cardiac monitors could mask emergencies or trigger false alarms
• Infusion pumps could be manipulated to deliver incorrect medication dosages
• Stakes far higher than data breaches in other sectors

Why Traditional Security Fails:
• Embedded firmware cannot be easily updated (vulnerabilities unpatched for years)
• Inadequate or absent network segmentation (allows lateral movement)
• Missing input validation (creates trivial attack vectors)
• Legacy systems designed before modern threats (cannot retrofit security)

PROCESS (LEFT PANEL)
=====================

Production-Grade Hospital Infrastructure:
• 9 Ubuntu Server VMs running on enterprise hardware
  - PostgreSQL database, MQTT broker, Node-RED automation
  - Grafana visualization, Mirth Connect HL7 engine, HAPI FHIR server
  - Wazuh SIEM, Keycloak identity management, HashiCorp Vault secrets

Data Pipeline Performance:
• 100 sensor readings per second through HL7 FHIR-compliant pipeline
• Cardiac data flows: MQTT → Node-RED → PostgreSQL (100 writes/sec)
• Rate-limited stream to Mirth Connect → HL7 FHIR transformation → HAPI server
• 53+ million heartrate records in active tables
• 87 GB of historical data in archive tables

Network Segmentation:
• VLAN 30 (10.30.0.0/24): Secure hospital infrastructure
• VLAN 2 (192.168.50.0/24): Isolated attack laboratory

Demonstration Methodology:
• Two identical pressure sensor systems, same hardware:
  - Raspberry Pi 5 controllers
  - DATAQ analog pressure sensors
  - ADS1115 ADC converters, BSS138 level shifters
  - Sequent relay HATs, solenoid valves, air pumps
  - Identical pressure vessels
• Only difference: Security implementation
  - Vulnerable: Accepts sensor data via unauthenticated Flask API, no input validation
  - Secure: Validates all incoming sensor readings against local I2C sensor measurements


=====================
ANALYSIS (CENTER PANEL)
=====================

Input Validation is Fundamental:
• Vulnerable system's unconditional trust of network data = trivial attack vector
• No sophisticated techniques needed
• No privilege escalation required
• No software vulnerability exploitation
• Attacker simply sends HTTP POST with false sensor values
• System accepts without question
• Mirrors real-world IoT compromises

Defense-in-Depth Approach:
• Effective IoT security requires multiple complementary layers
• Network segmentation: Limits attack surface exposure
• Intrusion detection: Provides visibility into attack attempts
• SIEM monitoring: Enables forensic analysis and incident response
• Identity management: Controls access to administrative functions
• Secrets management: Protects credentials from exposure
• Transport security: Prevents man-in-the-middle attacks
• Physical sensor validation: Creates hardware-rooted chain of trust
• Layered approach ensures protection even if individual controls are bypassed

RESULTS (RIGHT PANEL)
=====================

Attack Testing Methodology:
• 150 attack attempts against each system using attack_spoof.py in dual-target mode
• Simultaneous spoofed pressure readings to both systems at 10 Hz per target
• False claim: 0.0 PSI when actual measured pressure is 25 PSI

Vulnerable System (Pi #7 at 192.168.50.100):
• Accepted all 150 attacks (100% success rate)
• Zero detections logged
• Catastrophic vessel failure within 20 seconds
• Continuous pump activation based on false "empty vessel" readings
• Real pressure exceeded safe limits
• "Invisible attack" scenario: No indication to administrators until physical damage

Secure System (Pi #6 at 10.30.0.25):
• Rejected all 150 attacks (0% success rate)
• 100% detection and logging
• Each rejection logged to Wazuh SIEM with complete forensic info:
  - Source IP: 192.168.50.191
  - Claimed pressure: 0.0 PSI
  - Actual measured: 25.0 PSI
  - Sensor mismatch: 25.0 PSI (exceeds 1.0 PSI threshold)
  - Timestamp and rejection reason
• Maintained normal operation throughout attack
• Zero downtime or service degradation
